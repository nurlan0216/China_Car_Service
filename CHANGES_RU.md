# Что изменено

## 1. ⚠️ Безопасность (сделайте в первую очередь)
В `Config.gs` был захардкожен реальный `TELEGRAM_TOKEN`. Он уже "засветился"
(был вставлен в переписку) — считайте его скомпрометированным:
1. Telegram → @BotFather → `/mybots` → ваш бот → API Token → **Revoke current token**.
2. Новый токен впишите в `apps-script/1_Config.gs` → `setupConfig()`.
3. Один раз выполните `setupConfig()` из редактора Apps Script.
4. `TO_PASSWORD` больше не используется и убран из конфига — весь доступ
   теперь через личные аккаунты (см. ниже).

## 2. Апps Script backend (папка `apps-script/`)
В вашем zip был только фронтенд (html), сам код Apps Script вы прислали
текстом в чате — я обновил его и положил рядом отдельными файлами
(1_Config.gs … 7_WebApp.gs). Их нужно скопировать в ваш проект
Apps Script (script.google.com), заменив старые файлы. Порядок файлов
в редакторе не важен для работы, цифры — просто для удобства чтения.

**Новый лист "Админ"** создаётся автоматически при первом обращении.
Колонки:
1. `Имя` — логин сотрудника
2. `Пароль_хэш` — SHA-256 хэш (пароль в открытом виде не хранится)
3. `СуперАдмин` — TRUE/FALSE (или "Да"/"Нет") — **выставляется только
   вручную прямо в таблице**, через сайт это сделать нельзя
4. `Создано`

Чтобы кто-то мог редактировать объявление — зарегистрируйте его через
to.html, затем зайдите в Google Таблицу и впишите `TRUE` в колонку
"СуперАдмин" в его строке.

## 3. `to.html` (Учёт ТО)
Общий код доступа (020202) убран. Теперь:
- экран входа: **Имя + Пароль**, кнопка **"Войти"**;
- под ним ссылка **"Нет аккаунта? Регистрация"**, разворачивающая форму
  регистрации (имя, пароль, повтор пароля);
- новые аккаунты пишутся в лист "Админ" (по умолчанию не супер-админ);
- все запросы (поиск, добавление записи, скачивание PDF) теперь
  проверяются по личному логину/паролю вместо общего кода.

## 4. `announce.html` (Объявление для водителей)
- тот же личный вход (имя+пароль), что и в to.html;
- после входа сервер сообщает, супер-админ ли это (`isSuperAdmin`);
- **если да** — окно редактирования объявления показывается, работает
  как раньше (сохранить/очистить);
- **если нет** — окно редактирования скрывается, вместо него — короткое
  сообщение о том, что нужна роль супер-админа.

## 5. Рекомендации в кабинете водителя (driver.html) — исправлено
Раньше подсказки по маслу/фильтру появлялись, только когда пробег с
последней замены уже подходил к норме или превышал её — если машина
недавно обслуживалась, блок рекомендаций был **пустым**, из-за чего
казалось, что рекомендации вообще не работают.

Теперь `getDriverRecommendations()` **всегда** возвращает по одной
строке на масло и на фильтр (если по ним есть хоть одна запись в
истории), с статусом:
- 🟢 `ok` — пока в пределах нормы;
- 🟡 `soon` — приближается срок замены;
- 🔴 `due` — норма пробега превышена, пора менять;
- ⚪ `unknown` — по этому виду работ ещё вообще не было записи.

`driver.html` красит подсказку в соответствующий цвет.

## 6. Объявление теперь редактируется прямо в `to.html`, с фото/видео
Раньше редактировать объявление можно было только в отдельном файле
`announce.html`, с ещё одним экраном входа. Теперь:
- при входе в `to.html` статус супер-админа (`isSuperAdmin`) определяется
  сразу же — в том числе если сессия уже была сохранена в этой вкладке
  (раньше в этом случае сервер вообще не спрашивался повторно);
- если сотрудник — супер-админ, внизу главного экрана `to.html`
  появляется карточка **"📢 Объявление для водителей"** — то же самое
  редактирование (текст, сохранить, очистить), без перехода на отдельную
  страницу;
- добавлена возможность приложить к объявлению **фото или видео** —
  файл загружается на тот же Google Диск (подпапка "Объявления") и
  показывается водителям в `driver.html`: фото — сразу в тексте
  объявления, видео — ссылкой "🎥 Смотреть видео";
- `announce.html` при этом не удалён и продолжает работать как раньше —
  можно оставить как запасной вход или убрать из меню, если он больше
  не нужен.

## 7. Кабинет водителя: кнопка "Проверить следующее ТО"
Рекомендации по маслу/фильтру знают только пробег **на момент последней
записи в истории** — само приложение не может определить, сколько машина
проехала после этого (нет доступа к одометру или GPS). Поэтому сразу
после замены подсказка показывала "пройдено ~0 км", даже если машина уже
накатала тысячи километров, и это выглядело как ошибка.

Добавлена кнопка **"🔍 Проверить следующее ТО по текущему пробегу"** в
`driver.html`: водитель один раз вводит свой текущий пробег, сервер
(`apiCheckMileage` → `getMileageCheck()` в `3_History.gs`) сравнивает его
с последней записью о замене и сразу присылает совет (🟢/🟡/🔴), не трогая
саму историю обслуживания.

## 8. Убрана лишняя кнопка "Поделиться" у водителя
В `driver.html` было две кнопки для истории ТО — "Скачать PDF" и
"Поделиться PDF-историей" (через системное меню телефона). Вторая кнопка
убрана как избыточная — осталось только скачивание.

## 9. Ссылка для WhatsApp в акте (`act.html`) — без стороннего сервера
Раньше для кнопки "Отправить в WhatsApp" ссылка на PDF готовилась через
сторонний сервис `tmpfiles.org` — файл заново загружался туда только
ради временной ссылки. Теперь PDF и так сохраняется на ваш Google Диск
(см. `saveActPdfFromBase64_`), и сервер сразу возвращает эту ссылку в
ответе (`driveUrl`) — `act.html` подставляет её в текст сообщения
WhatsApp напрямую, без обращения к tmpfiles.org. Файлу на Диске
автоматически выставляется доступ "по ссылке", иначе клиент увидит
запрос на вход в Google-аккаунт вместо PDF.
Кнопка "🔗 Поделиться PDF" (системное меню телефона) в `act.html`
работает как раньше — она никогда не обращалась к стороннему серверу,
так что её не трогали.

## ЭТАП 5 — Защита от гонок при параллельной записи (LockService)
При одновременной работе нескольких пользователей (несколько сотрудников
или водителей одновременно регистрируются/сохраняют запись) возможны
гонки — Google Таблица сама по себе не гарантирует, что два параллельных
"прочитать → записать" не затрут или не задвоят строку. Все такие места
в `apps-script/2_Sheets.gs` и `6_WebApi.gs` теперь обёрнуты
`LockService.getScriptLock()`:
- `registerAdmin` — регистрация сотрудника;
- `registerDriverVehicle` — регистрация водителя (для этого выделена
  отдельная "безблокировочная" функция `setDriverPasswordForExistingRowUnlocked_`,
  чтобы регистрация не блокировала сама себя повторно, если попутно
  задаёт пароль на уже существующей старой строке);
- `setDriverPasswordForExistingRow_` — установка пароля для старой записи
  (используется отдельно, не только из регистрации);
- `addServiceRecord` — сохранение записи ТО (и неявное создание машины);
- `saveAct` — сохранение акта приёма-передачи (самое частое место гонки:
  `getLastRow()+1` без блокировки может дать два акта в одну строку);
- `issueDeviceToken_` / `removeDeviceToken_` — лист "Devices" (Этап 4);
- `apiSetAnnouncement` — сохранение общего объявления (только сама
  запись коротких свойств; загрузка фото/видео на Диск намеренно
  выполняется ДО блокировки, чтобы не задерживать остальных).

`5_PdfGenerator.gs` и `4_Telegram.gs` блокировкой не оборачивались — они
не читают/не пишут в общий лист Таблицы, генерация PDF и отправка в
Telegram/Диск специально остаются "снаружи" блокировки, чтобы очередь
других пользователей не росла из-за медленных сетевых операций.

## ЭТАП 6 — Пароль только в POST, экранирование от XSS
(а) Действия `search`, `vehicleinfo`, `pdf` и `listplates` раньше
принимали пароль сотрудника в GET query-строке (`?...&pw=секрет`) —
теперь они обрабатываются только в `doPost()` (`apps-script/7_WebApp.gs`),
пароль передаётся исключительно в теле POST-запроса. `to.html` (`doSearch`,
`downloadPdf`) переведён с `apiGet` на `apiPost` для этих действий.

(б) В `renderFilteredRows` (`to.html`) и `renderHistory` (`driver.html`)
добавлено/применено экранирование `escapeHtml()` ко всем полям из
истории ТО (дата, пробег, тип работы, описание, стоимость) перед
вставкой через `innerHTML` — раньше это был хранимый XSS: сотрудник мог
вписать в поле "Описание" вредоносный `<script>`/HTML, и он бы выполнился
у любого, кто потом откроет эту запись (в `to.html` — у других
сотрудников, в `driver.html` — у водителя). Заодно поправлена мелкая
ошибка в уже существовавшей `escapeHtml()` (числовой пробег `0`
превращался в пустую строку).

Остальные места с `innerHTML` в проекте (`act.html`: список дефектов,
шаг "Проверка данных") вставляют только то, что сотрудник/клиент вводит
сам себе на том же экране в момент составления акта — это не тот же
паттерн хранимого межпользовательского XSS, поэтому их не трогали.

## ЭТАП 7 — Кэш частых чтений + UX при отправке
- `apiGetAnnouncement()` (объявление, читает каждый водитель при каждом
  открытии `driver.html`) и `apiDriverCheckPlate()` (проверка "есть ли
  гос. номер", тоже при каждом открытии) теперь кэшируются через
  `CacheService.getScriptCache()` — 45 и 30 секунд соответственно.
  Кэш объявления сбрасывается сразу при сохранении (`apiSetAnnouncement`),
  кэш проверки номера — сразу при регистрации водителя/установке пароля,
  чтобы новые данные не "тормозили" до конца TTL.
- Кнопки, отправляющие `apiPost`/`apiGet` ("Войти", "Зарегистрироваться",
  "Сохранить запись", "Сохранить объявление" в `to.html`; "Войти",
  "Зарегистрироваться", "Сохранить и войти", "Проверить" в `driver.html`;
  "Войти" в `act.html`) теперь блокируются (`disabled` + временный текст)
  на время запроса — двойной клик/тап больше не может отправить дубль.
- Во всех трёх файлах добавлен `fetchWithRetry_()` — один автоматический
  повтор запроса через 1.5 секунды при сетевой ошибке (`fetch` reject),
  прежде чем показать пользователю "Ошибка сети".
